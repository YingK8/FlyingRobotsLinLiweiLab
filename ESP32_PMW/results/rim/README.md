# `results/rim/` — rim-tracked J(f) takes, and the whole-ring series

Two producers write into this directory and **their columns are not interchangeable**. Read
this before pooling anything.

| producer | takes | `agree_deg` reads | how solved |
|---|---|---|---|
| `ai/rim_track.py` | `2026-09-08_*`, `2026-09-09_*` | **3.6–4.3 deg** | RANSAC on the rim edge, under a VIRTUAL focal length (`VIRTUAL_F`) |
| `controller/pose/disc_axis.py` | `2026-09-24_*`, `2026-09-27_*` | **15–22 deg** | `disc_pose.segment_disc` + `conic.backproject_ellipse`, real rig intrinsics |

The gap is not data quality, it is the camera model: `rim_track` projects through a virtual
focal length and `disc_axis` through the calibrated rig. A `MAX_AGREE_MED_DEG` gate calibrated
on the first number rejects every good take from the second — which is exactly what happened
on 2026-09-27 and cost a day. Compare like with like, or use a gate that clears both.

`ai/rim_track.py` is **not runnable in this repo**: it imports `stereo_axis`, `_load_rig`,
`VIRTUAL_F`, `_min_plate` and `_trim_fit` from `ai/alignment_rate.py`, which is gitignored and
was never committed. It exists in no branch. So the whole-ring series below was solved with
`disc_axis`, and `disc_axis` is what any new take should use.

## The whole-ring series, 2026-09-24 and 2026-09-27

The rim experiment for the **whole ring** rotor, driven 90–150 Hz, 10 repeats a frequency. Same
measurement as the half-ring and no-ring campaigns, so the three can be plotted together —
with the producer caveat above kept in mind.

**Protocol.** One schedule per flash, `ai/make_tilt.py --design whole`. Each repeat:

```
all coils on -> EASE ramp 2.0 -> 5.0 Hz (5 s) then 5.0 -> f at 2.8 Hz/s
            -> hold 5 s (3 s above 100 Hz)
            -> cut coils A and C (channels 0,2)
            -> post 15 s          <- the delay after the tilt, raised from 10 s on 2026-09-24
            -> all coils off, frequency reset to 2 Hz, off wait 21.5 s
```

The two-segment ramp is **not** decorative. The single `1.0 -> f` segment this generator used
before crosses the ~4.9 Hz pull-in at ~1.6 Hz/s and the rotor was not reliably caught
(operator, 2026-09-24). `2.0 -> 5.0` over 5 s is 0.6 Hz/s through the crossing, which is that
segment's whole job, and it is borrowed from `controller/control/tilt_schedule.py` so the
generator and the runner cannot disagree about the schedule they fly.

**Ten repeats are recorded as two blocks of five**, with a pause between them. Measured heating
in this protocol is ~9 C a repeat at 90 Hz rising to ~14 C at 150 Hz against an all-off window
of 21.5 s that sheds only ~0.4–0.7 C, so ten back to back would climb to 100–145 C from
ambient. The pause does not lower that peak — the block SIZE does.

The board **starts on its own reset**, so the driver flashes first and then starts the recorder.
The recorder therefore begins ~4.5 s after the schedule does and the first ~4.5 s of each take
is not in the video. Not fatal (the ramp needs 5 s to reach 5 Hz) but it is unaccounted.

**Frame rate is per take, not per series** — see `frame_rates.txt` beside this file, which is
generated by `ai/alignment/run_rim_sweep.py::write_frame_rates()` and marks each take `use` or
`superseded`.

Two rate regimes are deliberately mixed, because raising the request did **not** raise the
rate. Measured 2026-09-27 at 640x400:

```
no rate requested            209.2 stereo pairs/s   (source only, no encoder)
requesting 271.3             207.8
requesting 271.3, no rotate  209.4                   (rotate180 costs nothing)
a real take, encoder running 193.7 - 204.4           (this is the binding number)
```

`271.3 fps` in `controller/camera/elp_camera.json` is a SENSOR-only figure from `modes.py`,
which has no encoder and no rotation. Over `open_source` the AVFoundation driver clamps a
higher request to **210.0**, and the pipeline delivers ~200. The pipeline is encoder-bound, not
sensor-bound — asking for more does not deliver more.

**640x400 is the only mode that both clears 200 fps and keeps the rotor in frame.** 320x240's
421.7 fps is a sensor CROP the rotor overflows — the ring fit lands on a 367 px ellipse in a
320 px image — and `disc_axis.solve` refuses it anyway, since the rig is calibrated at 640x400
and 320x240 is not a uniform rescale.

## How a take was validated before it went to the USB

`ai/alignment/process_block.py` solves, validates and uploads. A file existing is not data, so
it gates on four things, and the gates come from measured takes rather than from intuition:

| gate | value | why |
|---|---|---|
| frames solved | ≥ 50% of the take | the tracker legitimately loses the disc edge-on, but not for half a take |
| view A vs B | ≤ 28 deg median | good `disc_axis` takes read 15.1–19.6 over 29 alignment-rate takes |
| tilt span | ≥ 5 deg | the rotor must actually lean; this is the quantity the experiment is about |
| sign flips | reported, **not** gated | a disc normal is defined only up to sign, so a flip is bookkeeping |

**The tilt span is measured to the axis LINE, not the vector** (`|n · ref|`). Using the vector
sign puts a single failed sign carry at 180 deg: the 2026-09-27 take read a 179.2 deg "span"
when the axis was stable to 0.5 deg either side of the flip and had moved ~20 deg in total.
