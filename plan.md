# Plan: minimal codebase, then a formal attitude/estimation stack

## Problem & approach

The repository (`ESP32_PMW/`) has grown a live flight pipeline, four theory
chapters, offline design tooling, hardware characterization data, and several
superseded side-trees. The goal is to **first reduce it to a minimal, coherent
codebase**, then build the state-of-the-art attitude estimator/controller on that
clean base.

Two user decisions shape the work:

- **Cleanup is Moderate**, committed with `git rm`, so the working tree is clean
  and minimal while git history keeps every removed file recoverable.
- **The attitude/estimation work extends existing modules in place** — it does not
  create a parallel tree. Anything that needs no hardware is executed here (sims,
  self-checks, replays of existing `results/` and `data/`); hardware runs are
  scripted and handed over as operator protocols.

## Phases 1-5 — the attitude / estimation / sysID stack (follows Phase 0)

Built by extending existing modules in place, each shipping a `demo()`/`_self_check()`
and a `theory.md` section, per the repo's conventions.

### Phase 1 — Formal gyroscopic-disk attitude model
- Extend `controller/control/hover_model.py` with an explicit rigid-body attitude
  model: Euler's equations for a spinning disk (polar `I_s = 3.3578e-9`, transverse
  `I_t = 2.0373e-9`, gyroscopic coupling), magnetic tilt torque `τ = m×B`, quadratic
  aero drag `−k_d f|f|` and thrust `k_T f²`, plus a tether/rod reaction term.
- Derive and code the linearisation about trim (precession frequency, damping) and
  reconcile it with `ai/design/spatial_model.py` and `theory.md` ch. 11/12.

### Phase 2 — estimation at ~90 Hz
- The live pipeline runs 500 Hz control on ~90-100 Hz pose (CLAUDE.md). Extend
  `controller/control/predictor.py` into a latency-aware continuous-discrete
  observer (model-forward propagation + delay compensation across the pose fix),
  with the gyroscopic attitude states added.
- Quantify the phase margin this costs at 90 Hz in `robust_cert.py`; assert a floor.

### Phase 3 — robust attitude system identification
- Extend `controller/control/sysid.py` with an attitude stage that identifies
  `(I_s, I_t, k_d, k_T, k_lat, thrust-axis bias ψ, tether stiffness)` with explicit
  uncertainty bounds — errors-in-variables / frequency-domain fits over existing
  `results/tilt_sweep` and `data/` captures, refusing fits below the noise floor
  (the `attitude.fit_rotation` "refuse rather than guess" pattern).
- Replay the existing takeoff CSVs to auto-report the takeoff/capture frequency and
  reconcile it with `takeoff_report.py` and `constants.RAMP_*`.

### Phase 4 — feedforward + robust attitude control
- Extend `controller/control/attitude.py` with a model-based feedforward trim
  (inverse dynamics of Phase 1) feeding the existing `TiltController`, with the
  measured `rot_deg` and the `robust_cert.py` certified region as hard gates.
- Add the tether-augmented variant for the tethered case.

### Phase 5 — experiment loops
- Tethered: extend `controller/control/tilt_servo.py` (the rod/mast rig) into a
  scripted tethered-attitude experiment with the feedforward trim.
- Free flight: an `attitude.py`-driven free-flight attitude loop (hold-upright,
  step response), reusing `hover_controller_runner` safety (thermal pacing,
  `safe_off`, GPIO14).
- Both: offline-validated + replayable; hardware steps emitted as operator
  protocols, not run here.

## Notes / risks

- The tether reaction enters the model but is **not** yet characterised; Phase 3
  must identify it before Phase 4's tether variant closes a loop.
- `k_lat` is still a seed guess (`hover_model.py:70`) and `rot_deg` has no default
  (`attitude.py`) — both are identification gates, and the plan does not let a
  controller arm past them.
- Deleting `writeup` scope data is fine for the flight path, but the prose
  citations "writeup 3.2/3.5" must keep resolving — hence the docx/pages stay.
